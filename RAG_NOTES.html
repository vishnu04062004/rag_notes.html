01 / RAG Fundamentals

01What is RAG, and why is it important?＋

Retrieval-Augmented Generation (RAG) is a technique that retrieves relevant external information and provides it to a language model as context before generating an answer.

Why use it?

  • Grounded answers: Responses can be based on retrieved evidence.
  • Fresh knowledge: Update the knowledge base without retraining the LLM.
  • Private knowledge: Use internal documents, manuals, or company data.
  • Traceability: Retrieved sources can support citations and verification.
  • Cost: Often cheaper than fine-tuning a model just to teach it new facts.

RAG does not guarantee correctness. Bad retrieval, misleading documents, or poor reasoning can still produce hallucinations.

Interview line: RAG connects an LLM's generative ability with an external, updateable knowledge source.
02Explain the basic architecture of a RAG system.＋

A typical RAG system has an offline indexing pipeline and an online query pipeline.

OFFLINE
Documents → Parse → Clean → Chunk → Embed → Index

ONLINE
User Query → Query Processing → Retrieve
           → Rerank → Build Context → LLM
           → Answer + Sources
  • Indexing: Converts source documents into searchable representations.
  • Retrieval: Finds chunks relevant to the user's question.
  • Generation: Uses the retrieved context to formulate an answer.

Some systems add hybrid search, query rewriting, access-control filters, a reranker, or an evaluation layer.

03What are the key components of a RAG pipeline?＋
  1. Document loaders: Read PDFs, webpages, DOCX files, databases, and other sources.
  2. Parser and cleaner: Extract meaningful text and remove noise.
  3. Chunker: Splits documents into manageable passages.
  4. Embedding model: Converts text into dense numerical vectors.
  5. Index / vector database: Stores vectors, text, and metadata.
  6. Retriever: Finds relevant documents using vector, lexical, or hybrid search.
  7. Reranker: Reorders candidates using a more precise relevance model.
  8. Prompt builder and LLM: Combine the query and evidence to generate an answer.
  9. Evaluation and monitoring: Measure retrieval quality, grounding, latency, and cost.
04What is chunking? How do you choose chunk size?＋

Chunking splits a large document into smaller units that can be independently indexed and retrieved.

Very small chunks may lose context. Very large chunks may contain irrelevant information, reduce retrieval precision, and consume more context-window space.

There is no universally optimal chunk size. As an initial experiment, try approximately 300–800 tokens with a modest overlap, then tune it against a representative evaluation dataset.

Factors to consider

  • Document structure and average paragraph length.
  • Question types and how much context answers typically require.
  • Embedding model and model context-window limits.
  • Retrieval recall, precision, latency, and token cost.

Keep headings and source metadata with each chunk. Preserve tables and code as coherent units where possible.

05Compare fixed-size, semantic, and recursive chunking.＋
  • Fixed-size: Splits by a set token or character length. Simple, fast, and predictable, but may cut ideas in half.
  • Recursive: Tries separators in order, such as sections, paragraphs, sentences, and finally smaller units. A practical general-purpose default.
  • Semantic: Uses meaning or embedding similarity to identify topic boundaries. Can preserve coherent ideas but requires more computation and tuning.

Example: A legal contract benefits from section-aware recursive splitting. A long narrative with topic transitions may benefit from semantic splitting.

Choose based on measured retrieval quality, not on the assumption that the most sophisticated method is always best.
06What is Contextual Retrieval?＋

Contextual Retrieval enriches a chunk with explanatory context from its parent document before indexing it, helping a standalone passage retain information that would otherwise be lost.

Example chunk: “It increased by 15%.”

Without context, the subject is unclear. Enrichment might produce: “In the 2025 sales report, revenue increased by 15% year over year.”

The enriched representation can be used for embeddings and/or lexical indexing, while the original passage is preserved for citations and answer generation.

Benefits include better retrieval for references, acronyms, and isolated statements. Trade-offs include preprocessing cost, extra index storage, and the risk of introducing incorrect context.

07What are embeddings? How does text become a vector?＋

An embedding is a numerical vector produced by a trained model to represent information in a space where semantic relationships can be compared.

  1. Tokenize the text.
  2. Pass the tokens through the embedding model.
  3. Pool or otherwise transform model representations into a fixed-size vector.
  4. Store the vector with the text and metadata.
  5. Embed the query using a compatible model and compare it with indexed vectors.

Similarity is often measured with cosine similarity, dot product, or Euclidean distance, depending on the model and index configuration.

Semantically similar passages may have nearby vectors, but embeddings do not understand facts perfectly and can struggle with exact identifiers or subtle negation.

08How do you choose an embedding model?＋
  • Retrieval quality: Benchmark on your actual domain and questions.
  • Language coverage: Check multilingual and domain-specific performance.
  • Latency and throughput: Consider indexing and query-time speed.
  • Vector dimension: Higher dimensions can increase storage and search costs.
  • Deployment: Compare hosted APIs with local models and their privacy implications.
  • Licensing and cost: Check commercial-use rights, pricing, and infrastructure requirements.

Use a fixed evaluation set and compare Recall@k, MRR or nDCG, latency, and cost. Query and document encoding may use different instructions or modes for some embedding models.

Important: If you change the embedding model, you generally need to re-embed the corpus. Vectors from incompatible embedding spaces should not be compared directly.

02 / Retrieval & Search

09What is Agentic RAG?＋

In Agentic RAG, an LLM or agent decides which retrieval actions to take, potentially across multiple steps, tools, or knowledge sources.

A simple RAG pipeline usually follows a fixed retrieve-then-generate path. Agentic RAG can rewrite queries, retrieve again, call SQL tools, inspect evidence, and decide whether it has enough information.

Advantages: Flexible workflows, iterative retrieval, multi-step reasoning.

Disadvantages: More latency, cost, complexity, and opportunities for incorrect tool use.

Use it when questions genuinely require multiple actions. Prefer ordinary RAG for straightforward questions because it is easier to test and operate.

10Hybrid search vs. pure vector search?＋

Vector search retrieves by semantic similarity. Lexical search, such as BM25, retrieves based on matching terms and their statistical importance.

  • Vector search is useful for paraphrases and conceptually related questions.
  • BM25 is useful for exact names, error codes, product IDs, acronyms, and rare keywords.
  • Hybrid search combines both, often using Reciprocal Rank Fusion (RRF) or a learned combination.

For example, a query about error code ERR-4921 may benefit greatly from lexical matching even if the semantic embedding is weak.

Hybrid search is a strong baseline for varied enterprise documents, but its value should be verified on the target corpus.

11What is reranking, and why is it useful?＋

Reranking is a second-stage ranking step applied to an initial set of retrieved candidates.

Query → Retrieve top 50 candidates
      → Rerank candidates
      → Keep best 5–10
      → Generate answer

A bi-encoder embedding model encodes the query and documents separately, enabling efficient candidate retrieval. A cross-encoder evaluates the query and each candidate together, usually yielding a more query-specific relevance score.

Reranking can improve the quality of the final context, but adds compute and latency. Retrieve enough candidates for good recall, then rerank a manageable set.

12What is ColBERT and what is late interaction?＋

ColBERT is a neural retrieval approach that uses token-level representations for both the query and document instead of compressing each into a single vector.

In late interaction, query and document tokens are encoded separately. At scoring time, each query token is matched against document token representations, and the best matches are aggregated, commonly with a MaxSim-style operation.

This preserves more fine-grained token matching than a single-vector embedding while allowing document representations to be precomputed.

Its trade-off is greater index size and more complex scoring compared with simple single-vector retrieval.

13Compare cross-encoder, ColBERT, and LLM rerankers.＋
  • Cross-encoder: Processes the query and each candidate together. Strong pairwise relevance scoring, but candidates are scored individually.
  • ColBERT / late interaction: Uses token-level representations and efficient interaction scoring. Can balance fine-grained matching and retrieval throughput.
  • LLM reranker: Uses a generative model to assess relevance or order candidates. Flexible for complex criteria but may be expensive, slow, and sensitive to prompt design.

Choose using retrieval metrics, latency, cost, hardware, and corpus scale. A small cross-encoder often provides an effective production baseline.

14How do you answer questions that require multiple documents?＋

These are multi-document or multi-hop questions. A single retrieval step may find only one part of the evidence.

  1. Identify the separate facts or subquestions needed.
  2. Decompose the original query into targeted subqueries.
  3. Retrieve evidence for each subquestion.
  4. Deduplicate, rerank, and retain the evidence with source identifiers.
  5. Combine the evidence and verify that it supports the final conclusion.

Graph-based retrieval, iterative retrieval, or an agent can help when the evidence is linked across entities or documents. Do not assume that the LLM can infer a missing fact simply because it has some relevant passages.

15What is the “Lost in the Middle” problem?＋

LLMs can use information less reliably when relevant evidence appears in the middle of a long context than when it appears near the beginning or end. The effect varies across models and tasks.

Mitigation strategies:

  • Retrieve fewer, higher-quality passages.
  • Place the strongest evidence prominently in the prompt.
  • Remove redundant and irrelevant chunks.
  • Use reranking and context compression.
  • Evaluate evidence placement with the actual target model.

A larger context window is not a substitute for good retrieval and context organization.

16How do you evaluate a RAG system?＋

Evaluate retrieval and generation separately, then assess the complete system.

  • Context precision: How much of the retrieved context is relevant?
  • Context recall: How much of the needed evidence was retrieved?
  • Faithfulness: Are the claims in the answer supported by the supplied context?
  • Answer relevance: Does the response address the question?
  • Correctness: Does the answer match a trusted reference answer or verified facts?
  • Retrieval metrics: Recall@k, Precision@k, MRR, and nDCG.
  • Operations: Latency percentiles, error rates, cost per query, and throughput.

Use a representative, held-out evaluation dataset. Automated LLM-as-judge metrics are useful but should be calibrated against human judgments and known examples.

17What is Self-RAG? How does it decide when to retrieve?＋

Self-RAG is a framework that trains a model to reflect on retrieval and generation, using special reflection tokens to guide decisions about retrieving, assessing relevance, and evaluating support for generated claims.

Its key idea is that retrieval should not be blindly applied to every query. A system should consider whether external evidence is necessary and whether the retrieved evidence is useful.

A simpler production implementation can use a query classifier or an LLM-based router to decide between direct answering, retrieval, or clarification. This is inspired by adaptive retrieval, but is not identical to the original Self-RAG method.

18GraphRAG vs. traditional RAG?＋

Traditional RAG typically retrieves text passages using vector, lexical, or hybrid search.

GraphRAG organizes information around entities and relationships in a graph. Some implementations also create summaries of graph communities to answer broader, corpus-level questions.

  • Traditional RAG is usually simpler and effective for passage-level questions.
  • GraphRAG can help with relationship-heavy, multi-hop, or global questions spanning many documents.
  • Graph construction, entity resolution, and graph maintenance introduce additional cost and complexity.

Use graph-based approaches when relationship structure adds measurable value, not merely because a knowledge graph sounds advanced.

19What is Vectorless RAG?＋

Vectorless RAG is a broad term for retrieval approaches that do not rely on dense vector similarity as their primary search mechanism.

Examples include BM25, full-text search, SQL queries, metadata filtering, structured indexes, and search over document summaries or hierarchies.

It can be useful for exact terms, structured facts, identifiers, or situations where embedding generation and vector storage are undesirable.

It does not mean retrieval disappears. It means the system uses other representations or search mechanisms. Many practical systems combine vectorless methods with vector retrieval.

20How do you handle structured data, tables, and SQL in RAG?＋

First identify whether the question requires unstructured text, exact structured values, or both.

  • Structured facts: Query the relational database using SQL.
  • Explanations and policies: Retrieve relevant documents.
  • Mixed questions: Combine SQL results and document evidence.

For tables, preserve headers, units, row relationships, and captions. A row should retain the column names that give its values meaning.

For text-to-SQL, validate generated queries, use read-only permissions, allowlist tables and columns, enforce timeouts, and never trust model-generated SQL blindly.

A vector database is not a replacement for a relational database when the task requires exact aggregation, joins, or filtering.

03 / Advanced RAG Techniques

21What are common RAG failure modes, and how do you debug them?＋
  • Relevant document not retrieved: Inspect query formulation, chunking, embeddings, filters, and search settings.
  • Relevant document retrieved but ranked low: Try hybrid search, increase candidate depth, or add reranking.
  • Correct evidence but incorrect answer: Check prompt instructions, context ordering, conflicts, and generation behavior.
  • Incomplete answer: Check whether all necessary evidence was retrieved.
  • Stale answer: Check ingestion timestamps, deletion handling, and index freshness.
  • Wrong source: Check metadata, permissions, ranking, and duplicate content.

Log the query, rewritten query, retrieved chunk IDs and scores, filters, final context, answer, and latency for each stage. Reproduce failures with a test dataset before changing the system.

22How do you handle document updates and freshness?＋
  1. Assign stable document IDs and track versions or content hashes.
  2. Detect new, modified, and deleted documents.
  3. Re-parse and re-embed changed content only when appropriate.
  4. Upsert the latest chunks and remove obsolete chunks.
  5. Track ingestion status, timestamps, and indexing errors.
  6. Use versioned or staged indexes where safe deployment is necessary.

For frequently changing facts, consider querying the authoritative database directly. Define acceptable freshness and monitor the delay between a source update and retrieval availability.

23How do you optimize RAG latency?＋
  • Use efficient approximate nearest-neighbor indexes where appropriate.
  • Reduce unnecessary query rewriting and repeated retrieval calls.
  • Retrieve a sensible candidate count, then rerank a smaller set.
  • Cache query embeddings or retrieval results when safe and useful.
  • Parallelize independent retrieval calls.
  • Limit final context size and avoid unnecessary prompt tokens.
  • Stream generated responses when appropriate.
  • Measure latency by stage and optimize the actual bottleneck.

Track p50, p95, and p99 latency, not only average latency. Caching must respect permissions, freshness, and tenant boundaries.

24How does metadata filtering work in RAG?＋

Metadata filtering restricts the searchable documents using attributes such as tenant ID, access level, document type, date, department, or language.

For example, a search may retrieve semantically relevant passages only from the user's permitted department and the latest approved policies.

Filters may be applied before retrieval, during candidate selection, or through a post-filtering step, depending on the search engine.

Pre-filtering can improve relevance and security, while post-filtering may leave too few results. Security-sensitive restrictions must be enforced by trusted backend logic, not merely by an LLM-generated filter.

25RAG vs. fine-tuning: when should you use each?＋
  • RAG: Best when answers depend on changing facts, private documents, citations, or a large external knowledge base.
  • Fine-tuning: Best when you want to change model behavior, style, task performance, or output patterns using training examples.
  • Both: Fine-tune for a desired behavior and use RAG to provide current, task-specific evidence.

Fine-tuning is not a reliable substitute for an updateable knowledge source. RAG is not a substitute for training when the model consistently lacks the behavior needed to perform a task.

Interview shortcut: facts that change → consider RAG; behavior that must change → consider fine-tuning.
26Why not just put the entire knowledge base into a long context window?＋
  • Token cost: Large prompts consume more input tokens.
  • Latency: Processing lengthy contexts may be slower.
  • Attention dilution: Relevant facts can be overlooked among irrelevant information.
  • Scale: The corpus may exceed the model's context limit.
  • Access control: Selective retrieval can reduce unnecessary exposure of sensitive data.

Long context can be useful for small corpora, complete-document reasoning, or tasks where many passages must be considered together. RAG is generally more scalable when the knowledge base is large.

27Explain HyDE, query decomposition, and step-back prompting.＋
  • HyDE: Generates a hypothetical answer or document from the query, embeds that text, and uses the vector to retrieve potentially relevant real documents. The hypothetical text is a retrieval aid, not trusted evidence.
  • Query decomposition: Splits a complex question into smaller subquestions and retrieves evidence for each.
  • Step-back prompting: Reframes a specific question into a broader conceptual question to retrieve underlying principles or background knowledge.

These techniques can improve recall for difficult queries but may add latency and introduce query drift. Evaluate them against simpler retrieval before deploying them.

28How do you implement citations and source attribution?＋
  1. Store source IDs, document titles, page numbers, URLs, and chunk offsets during ingestion.
  2. Carry source metadata through retrieval and reranking.
  3. Ask the LLM to cite only supplied source identifiers.
  4. Validate that every cited identifier exists in the retrieved context.
  5. Where possible, verify that the cited passage actually supports the associated claim.

Do not invent page numbers or citations after generation. For high-stakes applications, use claim-level attribution and human review rather than relying only on the presence of a citation.

29How would you scale RAG to millions of documents?＋
  • Use scalable storage and a vector or search index suited to the corpus and workload.
  • Batch document processing and embedding generation.
  • Use asynchronous, incremental ingestion instead of rebuilding everything for each update.
  • Choose an appropriate ANN index and tune recall versus latency.
  • Partition or shard data where it improves operational performance.
  • Apply metadata filtering, tenant isolation, and deduplication.
  • Monitor index size, throughput, query latency, ingestion lag, and retrieval quality.

At this scale, operational reliability matters as much as retrieval algorithms: retries, idempotent ingestion, backups, index migrations, and observability are essential.

30What is parent-child chunking?＋

Parent-child chunking indexes small child chunks for precise retrieval but associates them with larger parent sections for additional context.

Document
  └── Parent section
       ├── Child chunk A
       ├── Child chunk B  ← retrieved match
       └── Child chunk C

Retrieve child B → return parent or
a bounded surrounding section

Small children can improve matching precision, while the parent restores context for generation. The trade-off is that returning entire parents can increase prompt size and reintroduce irrelevant text.

04 / Production Scenarios & Debugging

31The right context is retrieved, but the LLM still hallucinates. Why?＋

Retrieval success does not guarantee generation success. The model may ignore evidence, misinterpret it, combine contradictory passages, or answer from prior knowledge.

Debugging approach:

  1. Inspect the exact final prompt, not just the retrieved chunks.
  2. Check whether the evidence directly answers the question.
  3. Remove noisy or contradictory passages and improve ordering.
  4. Instruct the model to distinguish supported facts from unknown information.
  5. Require citations and validate claim-to-source support.
  6. Test with adversarial and insufficient-context examples.

If the evidence is insufficient, the system should ask for clarification or abstain rather than fabricate details.

32How do you choose chunk overlap, and what happens if it is too high?＋

Overlap repeats a portion of text between adjacent chunks so that ideas crossing a chunk boundary are less likely to be lost.

Too little overlap may split definitions or procedures. Too much overlap creates redundant vectors, increases storage and indexing costs, and can cause near-duplicate retrieval results to crowd out diverse evidence.

Start with a modest overlap, perhaps 10–20% of the chunk length, then evaluate. Structure-aware chunking may reduce the need for overlap. Deduplicate retrieved passages when necessary.

33Retrieval is slow for a large knowledge base. How do you debug it?＋

Break down the total query time into embedding, search, filtering, reranking, context construction, and generation.

  • Check index configuration, memory pressure, shard distribution, and query selectivity.
  • Reduce candidate count only if retrieval quality remains acceptable.
  • Use efficient ANN search and appropriate batching.
  • Optimize expensive metadata filters and reranking.
  • Cache repeat queries where safe.
  • Measure p95 and p99 latency to identify outliers.

Do not optimize vector search first if generation or reranking is actually dominating latency.

34How do you prevent duplicate results in retrieval?＋
  • Deduplicate identical files using content hashes.
  • Use canonical document IDs and stable chunk IDs.
  • Remove repeated boilerplate where appropriate.
  • Collapse identical or near-identical chunks during retrieval.
  • Use diversity-aware ranking, such as maximal marginal relevance (MMR), when appropriate.

Do not blindly remove every similar chunk: two passages may look similar but belong to different versions, products, or policies. Preserve source identity and version information.

35How do you implement per-user access control in RAG?＋

Enforce authorization before restricted content can enter the model's context.

  1. Authenticate the user and determine trusted permissions.
  2. Associate each document and chunk with tenant and access-control metadata.
  3. Apply server-controlled permission filters during retrieval.
  4. Revalidate access for cached results and source links.
  5. Prevent cross-tenant leakage in caches, logs, and background jobs.
  6. Test with users who should and should not access each document.

Never rely on a prompt such as “do not reveal confidential information” as the primary security boundary. The model should never receive unauthorized evidence in the first place.

36How do you handle domain-specific jargon and acronyms?＋
  • Use a domain-relevant embedding model when benchmarks justify it.
  • Combine dense retrieval with BM25 or exact keyword search.
  • Expand known acronyms and aliases during indexing or query processing.
  • Preserve technical identifiers, equations, and code during parsing.
  • Include definitions and glossary entries in the searchable corpus.
  • Evaluate using real queries from domain experts.

Query expansion should preserve the original query because generated expansions may be incorrect or change its intent.

37How would you extend text RAG to images, charts, and tables?＋

Build a multimodal ingestion pipeline that preserves relationships between visual content and its source document.

  • Images: Use OCR, captions, visual embeddings, or a vision-language model as appropriate.
  • Tables: Preserve headers, row-column relationships, units, and captions; consider structured extraction.
  • Charts: Extract labels, axes, units, legends, and values when possible.
  • Retrieval: Search extracted text, structured records, image embeddings, or a combination.
  • Generation: Supply relevant text, table data, or original image crops to a capable model.

Always retain source-page and region metadata so the system can cite or display the original evidence.

38How do you version a RAG knowledge base?＋

Track the version of the source content and the processing configuration that produced each index.

  • Document version, content hash, source timestamp, and deletion status.
  • Parser, chunking strategy, and chunking parameters.
  • Embedding model and version.
  • Index schema and configuration.
  • Ingestion job ID, status, and error details.

For a major re-index, build a new index, run quality checks, switch traffic only after validation, and retain a rollback path. Avoid mixing incompatible embedding spaces without a deliberate migration plan.

39A multi-hop question fails even though each individual fact exists. Why?＋

The system may retrieve only one fact, fail to connect entities across passages, or make an unsupported inference between them.

For example, answering “Which team manages the product owned by the company that acquired X?” requires several linked facts.

  1. Break the question into explicit hops.
  2. Retrieve evidence for the first relation.
  3. Use that result to formulate the next query.
  4. Preserve evidence and provenance for every hop.
  5. Verify the final relationship across all supporting sources.

Graph retrieval, query decomposition, and iterative retrieval can help. Evaluate each hop separately to identify where the chain breaks.

40What if retrieved documents contradict each other?＋

Do not simply let the LLM choose whichever statement appears most convincing.

  • Check document timestamps and versions.
  • Prefer authoritative sources according to a defined source hierarchy.
  • Distinguish current policy from historical records.
  • Preserve provenance for both claims.
  • Use explicit conflict-resolution rules where the domain requires them.
  • If the conflict cannot be resolved, explain the discrepancy or escalate.

Source authority and recency should be encoded as explicit signals rather than assumed to be reflected in vector similarity.

41How do you prevent outdated answers when knowledge changes frequently?＋

Freshness depends on both the source of truth and the time taken to make updates searchable.

  • Use incremental ingestion with change detection.
  • Track document versions and effective dates.
  • Remove superseded records or mark them as historical.
  • Apply freshness-aware ranking where appropriate.
  • Use direct database or API lookups for rapidly changing values.
  • Invalidate caches when relevant data changes.
  • Monitor ingestion lag and test that deletions propagate.

A current timestamp on a chunk does not guarantee that its contents are current. Validate against the authoritative source.

42How do you handle complex PDFs with tables, columns, headers, and footnotes?＋

PDF extraction is a layout-understanding problem as well as a text-extraction problem.

  1. Determine whether the PDF contains selectable text or scanned images.
  2. Use layout-aware parsing and OCR when needed.
  3. Detect columns, headings, reading order, tables, captions, and footnotes.
  4. Preserve page numbers, section hierarchy, and table structure.
  5. Validate extracted output against representative original pages.
  6. Chunk according to logical sections rather than raw page boundaries alone.

For tables, retain headers with the values. For multi-column layouts, verify reading order. For scanned documents, inspect OCR quality and avoid silently indexing corrupted text.

05 / Bonus: Production-Ready Thinking

43How do you protect a RAG system against prompt injection in documents?＋

A retrieved document may contain malicious instructions designed to override the system prompt, reveal secrets, or trigger unsafe tool calls.

  • Treat retrieved content as untrusted data, not instructions.
  • Keep system instructions separate from source text.
  • Enforce authorization and tool permissions outside the model.
  • Do not allow documents to grant themselves access or authorize actions.
  • Validate tool arguments and restrict tools to least privilege.
  • Test with adversarial documents and indirect prompt-injection examples.

Prompt instructions alone are not sufficient security controls. Sensitive actions require trusted application logic and appropriate authorization.

44What would you monitor in a production RAG system?＋
  • Retrieval: Recall@k, relevance, empty-result rate, score distributions.
  • Generation: Correctness, faithfulness, citation validity, abstention quality.
  • Operations: Latency percentiles, error rates, throughput, availability.
  • Cost: Embedding calls, reranking calls, input/output tokens, storage.
  • Freshness: Ingestion lag, failed updates, stale records.
  • Security: Authorization failures, suspicious retrieval patterns, cross-tenant leakage tests.

Use privacy-conscious logs and avoid storing sensitive document content unnecessarily. Alerts should focus on meaningful regressions and user impact.

45How do you build a reliable RAG evaluation dataset?＋
  1. Collect representative real-world questions and edge cases.
  2. Associate questions with trusted answers and supporting source passages.
  3. Include unanswerable questions, ambiguous queries, and conflicting sources.
  4. Include exact-match, semantic, multi-hop, table, and domain-specific questions.
  5. Split development and held-out evaluation data to reduce overfitting.
  6. Compare changes using the same benchmark and inspect regressions manually.

Measure retrieval quality separately from answer quality. A final answer can look correct by coincidence even when retrieval failed, so end-to-end accuracy alone is insufficient for diagnosis.
